# GOAL1 (설계 초안, 시드 1 판정 후 확정): 목표 정보 + 양방향 29번도로를 정책 하나로

> 실험 기록 (가설, 판정 기준, 결과, 해석). 공통 조건은 `notes/04_experiments.md`

- **왜**: 스토리 다음 구간이 왕복 (무궁시티 ↔ 연두마을을 두 번 지남). 같은 29번도로 화면에서 정답 방향이 반대 → 화면만 보는 정책은 한 방향밖에 못 함. 여러 구간을 정책 하나로 하려면(T1에서 순차 학습은 잊음) 섞어 학습 + 목표 정보가 필요
- **준비 완료 (10-07, 학습 없이)**
  - 구간 `route29_rev`: 29번도로 서쪽 끝 (0,7) → 연두마을. 시작 상태 = route29 시연 마지막 칸 상태 (HP 같음)
  - 거리표: 491칸 탐색, 476칸, **최단 70걸음** (정방향 103: 턱을 동쪽으로는 뛰어내려 지름길로 씀 → 같은 도로라도 길이 다름)
  - 시연 72칸 (HP 17~19), 경로 밖 상태 395칸 (전투 중 상태 0, HP 17~19)
  - 녹화 버그 수정: (41,10)은 걸음 뒤 60프레임이 지나서야 인카운터가 시작돼서 "피했다"고 저장한 상태가 실제로는 전투 중이었음 → 기다리는 시간 120프레임 + 타이밍 후보 16가지. 기존 데이터(route29/newbark 시연, route29 경로 밖)는 검사해서 전투 중 상태 0 확인
- **설계 (안)**
  - 관찰: 화면 + 목표 맵 원핫 (구간의 goal_maps. 무궁시티 / 연두마을). 좌표나 방향은 안 줌 (그건 거리 보상 같은 선생님 신호가 됨). `--memory`와 같은 Dict 관찰 방식
  - 학습: 정책 하나, 환경 6개를 정방향 3 + 반대 방향 3. 구간마다 자기 시연 전선/폭 커리큘럼 (`route29_demo_lat` 규칙 그대로). 보상 `goal_only`, tile
  - 대조군: 같은 섞어 학습에서 목표 정보만 뺀 것 → 한쪽 방향으로 쏠리거나 둘 다 어중간할 것으로 예상. 목표 정보가 차이를 만든다는 직접 증거
- **판정 (안)**: 양방향 각각 경로 위 ≥ 80% (정방향은 LAT1 96~100%, 반대 방향 기준선은 따로 학습한 구간 전용 모델). 대조군은 한 방향 이상 < 50%
- **구현 (10-07)**
  - `GoldEnv(obs_goal=True)`: 관찰 Dict에 `goal` 96칸 = 목표 맵 그룹 원핫 32 + 번호 원핫 64 (구간의 goal_maps 첫 번째). 크기 고정 → 구간이 늘어도 신경망 입력 그대로. 확인: route29 (26,3) → 칸 26, 35 / route29_rev (24,4) → 칸 24, 36
  - `--goal` (env_config.json에 `obs_goal` 저장 → 진단/경로 밖/라이브/시청이 자동으로 따름). 정책은 MultiInputPolicy, 신경망 모양은 CnnPolicy와 같게 (MEM과 같은 방식) → 바뀌는 건 입력 96개뿐
  - `--env route29_bidir_lat`: 환경 i가 `parts[i % 2]` 구간을 맡음 (6개 → 정방향 3, 반대 3). 구간마다 LAT1 규칙(시연 전선 + 경로 옆 시작 25% + 폭)
  - `MultiDemoCurriculumCallback`: 구간별 전선/폭. TensorBoard `game/demo_front/<구간>`, `game/real_goal/<구간>`, `game/lat_*/<구간>`. 저장 `demo_ptr.json` = {구간: {ptr, radius}}
  - 라이브: 판마다 구간을 번갈아 (각자 자기 전선에서)
  - 시험: 환경 2개 2천 스텝 학습 → 구간별 기록 생김, 진단에서 관찰 모양 맞음 (시험 결과물은 지움)
- **확정 설계**
  - GOAL1_route29: `--goal` 켬. 예산 50만 (구간당 환경이 절반이라 구간당 경험도 절반. LAT1은 한 구간에 6환경으로 21~25만에 입구 도달 → 정방향은 약 2배 걸릴 것)
  - 대조군 GOAL1_nogoal (목표 정보만 끔)은 GOAL1이 되면 돌림 (목표 정보가 원인이라는 증거). 안 되면 대조군 없이 원인 분석부터
- **판정 기준 (확정)**
  - 정방향 route29 start/S2/S3 ≥ 80%, 반대 route29_rev start ≥ 80% → 정책 하나가 같은 도로를 목표에 따라 양방향으로 감. 왕복 구간으로 진행
  - 한 방향만 됨 → 목표 정보를 안 씀 (화면만으로 한쪽에 쏠림) 또는 예산 부족 → 구간별 전선이 둘 다 입구에 닿았는지 먼저 확인
  - 참고 기준선 (10-07 측정): LAT1(정방향 전용)을 route29_rev에서 → **도착 0%, 이탈 100%, 진행 0**. 시작하자마자 서쪽(무궁시티)으로 나감 = 화면만 보는 정책은 목표가 바뀌어도 늘 배운 방향으로 감
  - **목표 바꿔치기 시험 (외부 검토 반영, 결과 보기 전 추가)** `train.goal_probe`: 같은 게임 상태에 관찰의 목표만 바꿔 넣고 정책 출력 비교 (학습/진행 없음). 칸 80개 (route29 경로 밖 상태 중 두 거리표에 다 있는 칸, 경로 거리 4구간 × 20)
    - 기준선 LAT1 (목표 정보 없음): 목표 바꾸면 행동 바뀜 **0%**, 반대 목표에서 최고 행동이 맞는 방향 **5%** (정방향 55%. 맞는 방향 = 거리표상 거리가 줄어드는 이웃, 다른 유효 경로도 있어서 100%가 정답은 아님)
    - GOAL1 기준: 바뀜 ≥ 50%, 반대 목표 맞는 방향이 정방향과 비슷(± 15%p) → 목표 정보를 실제로 씀. 도착률은 되는데 바뀜이 낮으면 목표 말고 다른 단서로 구분하고 있는 것 (원인 분석)
  - **기준 수정 (10-08 09:20, 학습 7만 스텝 시점, 결과 보기 전, 외부 검토 반영)**: "목표 바꾸면 행동 바뀜"은 모든 칸이 아니라 **분기점**(두 목표의 거리표상 맞는 방향 집합이 겹치지 않는 칸)에서만 셈. 같은 칸이라도 두 목표의 최적 방향이 같은 경우가 섞이면 희석되기 때문
    - 기준선 LAT1: 분기점 39칸 / 80칸, 분기점 바뀜 **0%**, 분기점에서 반대 목표 맞는 방향 **0%** (정방향 77%)
    - GOAL1 기준: 분기점 바뀜 ≥ 50%, 분기점 반대 목표 맞는 방향 ≥ 50%
  - **기억을 뺀 영향은 따로 기록**: 혼동 통로 3칸은 기억 없는 LAT1(8%)과 비교 (LAT1_MEM 50%와 비교하지 않음)
  - 설계 사실 확인 (외부 질문): 환경이 구간별로 고정(정방향 3, 반대 3)이라 학습 스텝은 정확히 50:50. 에피소드 수는 반대 방향이 많음(짧아서) → 전선 판정용 판이 반대 방향에 더 빨리 쌓임. 전선/폭은 구간마다 독립 (시연 103칸 / 72칸)
  - 판정은 `train.report`(일반화 리포트) 한 표로: 경로 위, 반대 방향, 경로 밖, 빼둔 지역, 혼동 통로, 벽 고집, 목표 바꿔치기
  - 해석 주의: 경험을 반씩 나눠서 같은 스텝이면 LAT1보다 불리함. 비교는 "구간별 전선이 입구에 닿은 뒤"로
- **학습 중 관찰 (10-08 10:25, 30만)**: 두 방향 다 정체
  - 정방향 전선 52 (14.5만부터), 시작 (39,10)~(40,7) = U턴. 반대 방향 전선 55 (16.5만부터), 시작 (13,11)~(15,14) = **혼동 통로**. 전선 판 도착 26~42%
  - 목표 바꿔치기 (30만 체크포인트): 분기점 39칸 바뀜 **100%**, 반대 목표 맞는 방향 85%, 정방향 51% → 목표 정보는 씀
  - 전선에서 4판씩 추적: 실패 대부분이 **반대쪽 출구로 이탈**. 정방향은 U턴에서 동쪽으로 가 연두마을로, 반대 방향은 통로에서 서쪽으로 가 무궁시티로 = 다른 방향의 습관이 어려운 지점에서 새어 들어옴
  - 해석 (가설): 쉬운 곳에선 목표대로 갈리지만, 화면이 헷갈리는 곳(혼동 통로, U턴)에선 목표 정보만으로 부족. 혼동 통로는 LAT1_MEM에서 기억으로 풀렸던 곳 → 다음 후보 GOAL2 = GOAL1 + 기억
  - 결정: 사전 계획대로 50만까지 유지 (도중 변경 없음)
  - 10:55 확인: 전선 위치 20판 직접 측정 30만 9/20·7/20, 40만 6/20·8/20 → 실제 정체. 콜백 전선 도착률이 누적(마지막 당김 이후 전부)이라 긴 정체 뒤 반영이 느린 결함도 발견 (이번 정체의 원인은 아님)

- **판정**: 양방향 ≥ 80% **미달**, 분기점 바뀜 ≥ 50% **미달** (30만만 100%, 나머지 18%), 두 전선 입구 미도달 (52/103, 58/72)
- **원인 가설 (코드 확인, GOAL2로 검증 — 외부 검토: 아직 가설로 보는 게 정확)**: 신경망이 `net_arch=[]` = 화면 특징 512 + 목표 96을 이어 붙여 **은닉층 없이 선형으로** 행동을 냄 (기억 실험 때 "CnnPolicy와 같은 모양"으로 맞춘 결정을 그대로 씀)
  - 이 구조에서 목표는 모든 화면에 같은 쏠림(행동 선호의 상수 이동)만 더할 수 있음 → "이 화면 + 목표 A면 서쪽, 목표 B면 동쪽" 같은 화면 × 목표 상호작용을 표현 못 함
  - 데이터와 맞음: 목표 사용이 체크포인트마다 100% ↔ 18%로 출렁임 (쏠림 크기만 변함), 두 출발점이 각각 반대 목표 바로 옆이라 쏠림이 조금만 틀어져도 이탈, 끝내 한 방향으로 쏠림
  - 기억(LAT1_MEM)은 "직전 버튼"에 대한 쏠림만으로도 쓸모가 있어 이 한계가 안 드러났음
- **교훈**: "한 번에 하나만 바꾸기"를 위해 구조를 고정한 게, 새 입력이 화면과 엮여야 하는 실험에선 그 입력을 거의 무력화함. 입력을 추가할 땐 그 입력이 어떻게 쓰여야 하는지(상수 쏠림인가, 화면과 상호작용인가)를 먼저 따져야 함
- **다음**: E22 GOAL2 = GOAL1 + 은닉층 256-256 (`--hidden 256,256`). 기억은 그다음 (GOAL3). 시작할 때 기억이 비어 있어 출발점 이탈엔 도움이 안 되기도 함

- **정정 (10-08 12:20) — 목표 바꿔치기 시험 버그**: 리셋 직후 화면이 다시 그려지지 않아, 리셋만 반복하는 goal_probe는 **모든 칸을 같은 화면으로** 시험했음 (같은 숫자 12% / 18%가 여러 모델에서 반복된 이유). 위 표의 "분기점 바뀜" 값(100% / 18%)은 **무효**. 환경 수정 후 다시 잼:

| 모델 | 분기점 바뀜 | 정방향 맞는 방향 | 반대 맞는 방향 |
|---|---|---|---|
| LAT1 (기준선) | 0% | 97% | 3% |
| GOAL1 30만 | 62% | 67% | 56% |
| GOAL1 최종 | 56% | 64% | 62% |

  - **GOAL1도 목표를 꽤 썼음** (분기점 56~62%). "목표 사용이 100% ↔ 18%로 출렁임"은 착시
  - → "은닉층 없는 선형 결합이라 목표를 화면과 못 엮음" 가설은 **근거가 약해짐**. 선형 결합으로도 분기점 절반 이상은 목표대로 갈림
  - 실제 출발 0%의 더 직접적인 설명: **두 전선이 입구까지 못 감** (52/103, 58/72) → 출발 지점 근처를 한 번도 연습 안 함, 거기는 반대 목표 바로 옆이라 다른 방향 습관대로 이탈
  - 도착률 결과(정방향 0%, 반대 80%)와 판정 ❌는 유효 (진단은 게임을 진행해서 둘째 걸음부터 정상 화면)
